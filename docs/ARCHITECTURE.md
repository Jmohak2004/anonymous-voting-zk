# Architecture

## Identity and commitments

A voter identity is two random field elements `(nullifier, trapdoor)` generated in the browser.

- `commitment = Poseidon(nullifier, trapdoor)`: registered on-chain (public).
- `nullifierHash = Poseidon(nullifier, pollId)`: revealed when voting; unlinkable to the commitment, and different for every poll.

## Circuit (`circuits/vote_circuit.circom`)

`Vote(20)` has 11,435 constraints. It proves:

1. `commitment = Poseidon(nullifier, trapdoor)` is a leaf under `root` (Merkle path of depth 20, Poseidon(left, right), empty leaf = 0).
2. `nullifierHash = Poseidon(nullifier, pollId)`.

| Signal | Visibility | Meaning |
|---|---|---|
| `root` | public | Merkle root of the poll's registered commitments |
| `nullifierHash` | public | one-time tag for this poll |
| `pollId` | public | binds the proof to one poll |
| `vote` | public | chosen option index; binds the choice to the proof |
| `nullifier`, `trapdoor` | private | the secret |
| `pathElements[20]`, `pathIndices[20]` | private | Merkle path |

Public signal order consumed by the verifier: `[root, nullifierHash, pollId, vote]`.

## Contracts

- `Groth16Verifier` (generated by snarkjs from the final zkey).
- `IncrementalTree` library: append-only depth-20 Poseidon tree (`poseidon-solidity`), the root is updated on every insert in O(depth).
- `Voting`:
  - `createPoll(question, options)` - anyone; 2-8 options.
  - `register(pollId, commitment)` - Registration phase; one address once per poll; commitment must be non-zero, below the BN254 field order and unique.
  - `closeRegistration(pollId)` - creator; needs >= 1 member; freezes `root`.
  - `castVote(pollId, option, nullifierHash, a, b, c)` - Voting phase; anyone may submit (the proof is the authorization); checks option range, unused nullifier, then the proof against `[root, nullifierHash, pollId, option]`.
  - `endPoll(pollId)` - creator.
  - Views: `pollCount`, `getPoll`, `getTally`, `getCommitments`, `hasVoted`.

Phases are explicit: `Registration -> Voting -> Ended` (no timestamps).

## Data flow

```
browser                              chain
-------                              -----
createIdentity() -> localStorage
commitment ------------------------> register()      leaf inserted, root updated
                                     closeRegistration()  root frozen
getCommitments() <------------------ getCommitments()
build Merkle path, snarkjs proof
(proof, option, nullifierHash) ----> castVote()      verify, mark nullifier, tally++
```

## Shared TypeScript (`shared/zk.ts`)

`createIdentity`, `buildMerkleProof` (matches the on-chain tree, tested against it) and `generateVoteProof` (returns Solidity calldata order). Used by contract tests, `scripts/e2e.ts` and the frontend.

## Frontend notes

- Identities are stored per chain, contract, poll **and account** so two accounts in one browser do not overwrite each other.
- The identity is saved before the register transaction is sent. It is rolled back only if the transaction was never broadcast; if the tx is out but confirmation fails (replaced, RPC drop) the secret is kept, so a confirmed registration cannot lack its secret.
- An export/import backup lets a voter keep voting rights after clearing storage, or vote from a different address than they registered with.
